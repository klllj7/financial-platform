## 0. 요약

현재 구현은 **탐지 로직 자체는 골격이 잡혀 있으나, 그 로직을 감싸는 신뢰 경계가 없다.**
탐지기를 아무리 정교하게 만들어도 아래 두 가지 때문에 실효가 없다.

1. DLP 서비스(:8000)에 인증이 전혀 없고, 프런트에서 직접 노출된다 → 전 직원 프롬프트 원문이 무인증 조회된다
2. 멀티턴 대화에서 마스킹·차단이 무력화된다 → 1턴에서 막은 원문이 2턴에서 그대로 외부 LLM으로 나간다

기술 스택 관점에서 요청하신 Kong/NGINX, OpenTelemetry, Vault/KMS, Keycloak, FPE,
Llama Prompt Guard는 **현재 하나도 도입되어 있지 않다.** 다만 그중 상당수는 지금 단계에서
필요한 게 아니라서, §4 로드맵에서 실제 필요 시점과 함께 정리했다.

## 1. Current Architecture Review

### 1-1. 현재 흐름

```
브라우저
  │  /api/*      → (Vite proxy) → Node :8080  [JWT 인증 O]
  │  /dlp-api/*  → (Vite proxy) → FastAPI :8000  [인증 X]  ← 문제
  ▼
Node chat.service.sendMessage()
  ├─ ① inspectPrompt(입력)  → POST :8000/gateway/chat (direction=input)
  │      └ detect_pii(정규식) + detect_similarity(e5-large)
  │        → allowed / masked / blocked + usage_log·event_log 적재
  ├─ ② blocked면 LLM 호출 생략, 아니면 Solar/OpenAI 호환 API 호출
  ├─ ③ inspectPrompt(응답) → POST :8000/gateway/chat (direction=output)
  └─ ④ chat_messages 저장 → 응답 반환
```

역할 분담 자체는 합리적이다. 정규식은 구조가 정해진 PII를, 임베딩은 표현이 바뀐 의미 기반
기밀 요청을 맡는다. 문제는 그 바깥이다.

### 1-2. S1 — DLP 서비스 무인증 (Critical)

`vite.config.js`가 `/dlp-api`를 FastAPI로 직결한다. Node의 JWT 미들웨어를 타지 않는다.
그리고 `dlp/main.py`의 세 엔드포인트 중 **어디에도 인증·인가가 없다.**

```
GET  /events                  → 전 직원의 프롬프트 원문(description) 전량 반환
POST /gateway/chat            → user_id를 요청 바디로 받음
POST /events/{id}/action      → actor_user_id를 요청 바디로 받음
```

구체적 영향:

- **`GET /events`는 이 제품이 보호하려는 데이터 그 자체를 무인증으로 뱉는다.**
  `description`은 마스킹 이전 원문이다. 주민번호가 포함되어 차단된 프롬프트도 원문이 그대로 들어있다.
  프런트에서 호출하는 경로이므로 최소한 사내망 클라이언트에서 도달 가능하다.
- `actor_user_id`가 요청 바디에서 온다 → **감사 로그 위조가 가능하다.**
  "누가 이 위험 이벤트를 검토했는가"가 증빙의 핵심인데, 아무나 남의 이름으로 조치 이력을 남길 수 있다.
- `user_id`도 마찬가지 → 위반 이벤트를 타인에게 뒤집어씌울 수 있다.

Node 쪽은 `authenticate` + `authorize("COMPLIANCE_MANAGER")`가 제대로 걸려 있어서
대비가 더 선명하다. DLP 서비스만 무방비다.

### 1-3. S2 — 멀티턴 대화에서 마스킹·차단 무력화 (Critical)

`chat.service.js`에서:

```js
const previousMessages = await ChatMessage.findAll({ where: { sessionId } }); // 원문 그대로
const userMessage = await ChatMessage.create({
  content: [message, ...].join("\n"),        // ← 마스킹 안 된 원문을 저장
});
const providerUserMessage = { ...userMessage.toJSON(), content: inspection.safePrompt }; // 이번 턴만 마스킹
createSolarMessage([...previousMessages, providerUserMessage]);
```

**마스킹은 "이번 턴"에만 적용되고, DB에는 원문이 저장된다.**
다음 턴에서 `previousMessages`로 그 원문이 다시 로드되어 외부 LLM으로 전송된다.

재현 시나리오:

1. `제 주민번호는 901231-1234567입니다` → **차단됨**. LLM 호출 안 함. 그러나 원문이 `chat_messages`에 저장됨
2. 같은 채팅방에서 `안녕` 입력 → 통과
3. 대화 이력이 함께 전송되면서 **1턴의 주민번호 원문이 Upstage API로 나간다**

차단된 메시지조차 이력에서 걸러지지 않는다(`blocked` 플래그는 assistant 메시지에만 붙고,
`previousMessages` 조회는 플래그를 보지 않는다). 즉 **차단 기능이 지연된 유출로 바뀐다.**

### 1-3-1. S10 — 채팅방 제목에 원문 PII가 그대로 남는다 (Critical)

S2와 별개의 유출 경로다. 세션 생성이 `inspectPrompt` **이전**에 일어난다.

```js
const session = sessionId ? await findOwnedSession(...) : await ChatSession.create({
  title: message.length > 30 ? `${message.slice(0, 30)}…` : message,  // ← 검사 전 원문
});
...
const inspection = await inspectPrompt(combinedPrompt, userId);       // 검사는 그 다음
```

제목에 원문이 박히고, 목록 API·사이드바 어디에도 마스킹이 없다.
**차단된 프롬프트조차 제목으로는 원문이 화면에 노출된다.**

이건 가설이 아니다. 사용자가 보내온 화면의 사이드바에 실제로 이렇게 떠 있다.

```
000826-12345678 이 나이 때…
010-3375-3600
```

`GET /api/chats/sessions`는 인증만 통과하면 조회되므로, S1(무인증 `/events`)과 달리
로그인 사용자 본인 것으로 한정되긴 한다. 다만 **DB·백업·로그에 원문이 평문으로 남는다는 점**은 같다.

해결은 간단하다 — 세션 생성을 `inspectPrompt` 뒤로 옮기고 `inspection.safePrompt`로 제목을 만든다.

### 1-4. S3 — 정규식 우회 (High)

주민등록번호에 대해 흔한 난독화 8종을 실제로 넣어봤다. **전부 통과했다.**

| 입력 | 결과 |
| --- | --- |
| `주민번호 901231-1234567` | blocked |
| `주민번호 901231 - 1234567` (공백) | **allowed** |
| `주민번호 901231<제로폭>-1234567` | **allowed** |
| `주민번호 901231－1234567` (전각 하이픈) | **allowed** |
| `주민번호 9012311234567` (구분자 없음) | **allowed** |
| `주민번호 901231.1234567` | **allowed** |
| `주민번호 ９０１２３１-1234567` (전각 숫자) | **allowed** |
| `주민번호 OTAxMjMxLTEyMzQ1Njc=` (base64) | **allowed** |

원인은 패턴이 아니라 **정규화 단계가 없다는 것**이다. 패턴을 아무리 늘려도
NFKC 정규화·제로폭 제거·구분자 통일을 하지 않으면 변형마다 패턴을 추가하는 무한 술래잡기가 된다.

### 1-5. S4 — 긴 텍스트 희석으로 임베딩 탐지 우회 (High)

민감 문장 앞에 무해한 텍스트를 붙이면 유사도가 희석된다.

| 입력 | 유사도 | 마진 | 결과 |
| --- | --- | --- | --- |
| `고객 계좌 잔액이랑 최근 거래내역 전부 뽑아줘` | 0.963 | +0.112 | blocked |
| 일반 보고서 문장 60회 반복 + 같은 문장 | 0.891 | +0.007 | **allowed** |

문서 전체를 하나의 벡터로 평균내기 때문에 생기는 구조적 한계다.
첨부파일이 최대 2MB까지 허용되므로(`chat-upload.middleware.js`) **첨부파일을 통한 회피가 특히 쉽다.**
정규식은 길이와 무관하게 동작하므로 주민번호는 긴 텍스트 뒤에서도 잡힌다(확인함).
즉 **구조화된 PII는 안전, 의미 기반 탐지만 뚫린다.**

### 1-6. S5 — Fail-open (Medium)

```js
catch (error) {
  console.error("DLP 서비스 호출 실패, 탐지 없이 통과시킵니다:", error.message);
  return { blocked: false, maskApplied: false, safePrompt: message };
}
```

DLP가 죽어 있으면 **모든 프롬프트가 무검사로 외부 LLM에 전달된다.** `console.error`가 전부다.
개발 편의로는 맞지만 운영 기준으로는 정책 결정 사항이고, 최소한 (a) 환경변수로 fail-closed 전환,
(b) 실패 시 알림·메트릭, (c) 실패 건수 감사 기록이 필요하다.
지금은 DLP를 죽이는 것만으로 통제 전체가 무력화되고 흔적도 거의 남지 않는다.

### 1-7. S6 — 레이턴시 (High, 실측 완료)

**이전 점검의 "100~300ms" 추정은 틀렸다.** 실측하니 약 20배였다.
`detect_similarity()`를 길이별로 5회씩 돌린 중앙값이다 (Windows 11, CPU, e5-large).

| 입력 길이 | 임베딩 | 정규식 |
| --- | --- | --- |
| 34자 | 267 ms | ~0 ms |
| 119자 | 737 ms | ~0 ms |
| 221자 | 887 ms | ~0 ms |
| 323자 | 1,572 ms | ~0 ms |
| 442자 | 2,195 ms | ~0 ms |
| 646자 | **5,319 ms** | ~0 ms |
| 100KB | 6,682 ms | 188 ms |

대략 **문자당 5~8ms**로 선형 증가하다 512토큰에서 상한(약 6~7초)에 걸린다.
정규식은 100KB에서도 188ms라 사실상 무시 가능하다. **병목은 전적으로 임베딩이다.**

이게 요청당 **2회**(입력·출력) 일어난다.
사용자가 100자 질문 → AI가 600자 답변하는 평범한 대화에서 **DLP만으로 약 6초**가 붙는다.
LLM 응답 시간과 무관한 순수 오버헤드다.

원인은 두 가지다.

1. **모델 과대 선택.** `multilingual-e5-large`는 560M 파라미터다. 이 용도에 과하다.
   `multilingual-e5-small`(118M)이나 이미 로컬 캐시에 받아져 있는
   `paraphrase-multilingual-MiniLM-L12-v2`(양자화)면 5~10배 빠르다.
   **임계값 재측정이 필요하므로 모델 교체는 반드시 골든셋 측정과 함께 가야 한다.**
2. **동기 처리.** FastAPI 엔드포인트가 `def`(동기)라 기본 스레드풀(40)에서 돈다.
   ONNX 추론은 CPU 바운드라 동시 요청이 몰리면 스레드풀이 포화되고 큐잉이 폭증한다.
   `_model`은 전역 단일 인스턴스로 세션을 공유한다.

레이트리밋이 없으므로(S9) **긴 텍스트를 반복 전송하는 것만으로 CPU 고갈이 가능하다.**
S9의 등급을 실질적으로 끌어올리는 요인이다.

### 1-7-1. S11 — 512토큰 절단으로 첨부파일 대부분이 의미 검사 누락 (High)

S4(희석)와 원인이 다른 별개 문제다. e5 계열은 **512토큰(한국어 약 400~500자)에서 입력을 자른다.**
첨부파일은 최대 2MB까지 허용되는데(`chat-upload.middleware.js`),
**앞 500자만 유사도 검사를 받고 나머지는 임베딩 탐지 대상이 아예 되지 않는다.**

S4는 "긴 텍스트를 붙이면 평균이 희석된다"이고, S11은 "일정 길이 뒤는 읽지도 않는다"이다.
둘 다 §2-2의 청크 분할(Q6)로 동시에 해결된다.
정규식은 전체를 훑으므로 정형 PII는 계속 잡힌다(100KB 실측 확인).
- DB 적재(`usage_log`/`event_log`/`action_history` INSERT + commit)가 **응답 경로 안에서 동기로** 일어난다.
  탐지 결과를 돌려주기 전에 커밋을 기다린다.
- 스트리밍이 없다. Solar 응답을 `AbortSignal.timeout(60000)`로 통째로 기다린 뒤 출력 검사를 한다.
  사용자는 최대 60초 동안 빈 화면을 본다.

### 1-8. S7~S9 — 그 외

- **S7** `GET /events`가 전체 행을 조회한다. 페이지네이션·기간 필터가 없어 이벤트가 쌓이면 선형으로 느려진다.
  N+1은 이미 피해서 짜여 있다(일괄 조회).
- **S8** `policy_info.rule_content`(jsonb)와 `policy_history`가 부서별 정책용으로 이미 설계되어 있는데,
  **DLP는 이 테이블을 전혀 읽지 않는다.** 임계값과 패턴이 전부 파이썬 상수로 하드코딩되어 있어
  정책을 바꾸려면 배포가 필요하다. Dynamic Rule Engine의 토대가 이미 있는데 연결만 안 된 상태다.
- **S9** `app.use(cors())` — 전체 허용. rate limit, helmet 없음. FastAPI에는 CORS 미들웨어 자체가 없다.
  `regulationRoutes`/`policyRoutes`에는 `authenticate`가 아예 안 걸려 있다(다른 라우터는 모두 걸려 있음).
  JWT 만료 설정은 `auth.service.js:241`에서 확인 필요(이번 점검에서 미확인).
- **S12** `main.py`에서 `usage_log` 커밋과 `event_log`/`action_history` 커밋이 분리되어 있다.
  두 커밋 사이에서 실패하면 **탐지 기록 없는 사용 로그**가 남아 증적이 어긋난다.
  단일 트랜잭션으로 묶으면 된다(경미하지만 감사 대응에서 설명이 곤란해지는 유형).

### 1-9. 요청하신 스택의 현재 상태

| 항목 | 현재 | 비고 |
| --- | --- | --- |
| AI Gateway (Kong/NGINX) | **없음** | Vite dev proxy가 유일. 운영 환경 리버스 프록시 미구성 |
| OpenTelemetry | **없음** | `console.error`만 존재. 트레이스·메트릭 없음 |
| Vault / KMS | **없음** | `AI_CREDENTIAL_ENCRYPTION_KEY` 환경변수. 키 로테이션·감사 없음 |
| Keycloak | **없음** | 자체 JWT(`jsonwebtoken`). 그 자체는 문제 아님 |
| FPE (형식보존암호화) | **없음** | 마스킹은 `*` 치환 단방향. 복호 불가라 오탐 복구 불가 |
| 하이브리드 PII 탐지 | **부분** | 정규식 + 임베딩. NER(이름·주소·사번) 계층이 없음 |
| Llama Prompt Guard | **없음** | 인젝션 탐지는 정규식 13개 패턴이 전부 |

`credentialCrypto.js`는 AES-256-GCM을 올바르게 쓰고 있다(IV 랜덤, authTag 검증).
다만 키 파생이 `sha256(secret)`이라 KDF(PBKDF2/scrypt)가 아니고, 키 버전·로테이션 개념이 없다.

## 2. Reliability & Precision Optimization

### 2-1. 정규식 ↔ 임베딩 역할 분담 평가

**분담 원칙은 맞다.** 정규식은 형식이 고정된 식별자에, 임베딩은 표현이 자유로운 의미 판단에 쓰는 게 정석이다.
문제는 **두 계층 사이가 비어 있다**는 것이다.

| 대상 | 적합한 방식 | 현재 |
| --- | --- | --- |
| 주민번호·카드·계좌·전화 | 정규식 + 체크섬 | 정규식만 (체크섬 없음) |
| 이름·주소·사번·직위 | **NER** | **없음 — 완전 미탐** |
| 문맥 의존 판단 ("이 고객의 잔액") | 임베딩 / LLM 심사 | 임베딩 |
| 인젝션·탈옥 | 분류 모델 + 정규식 | 정규식만 |

가장 큰 공백은 **준식별자(quasi-identifier)** 다. `홍길동 과장 여신심사팀 사번 20190312`는
현재 전부 통과한다. 개별로는 PII가 아니어도 조합하면 특정 개인이 식별되는데, 금융권 DLP에서
실제로 문제가 되는 건 이 조합이다.

### 2-2. 오탐 방지 튜닝 포인트

지난 작업에서 임베딩 오탐은 정상 앵커 대비 마진 방식으로 해결했다(정상 28 / 민감 12 코퍼스 기준 FP·FN 0).
그 위에 더할 것:

1. **입력 정규화 파이프라인 (S3 대응, 최우선)**
   탐지 전에 NFKC 정규화 → 제로폭·제어문자 제거 → 구분자 통일(`.`/공백/전각 → `-`) →
   숫자만 남긴 사본 병행 스캔. 원문 오프셋 매핑을 유지해야 마스킹 위치가 어긋나지 않는다.

2. **체크섬 검증으로 오탐 제거**
   - 카드번호: Luhn 검증 → 임의의 16자리 숫자 오탐이 사라진다
   - 사업자등록번호: 가중치 체크섬
   - 주민번호: 2020년 이후 발급분은 검증번호가 폐지되어 **체크섬을 쓰면 미탐이 생긴다.** 쓰지 말 것
   현재 계좌번호에 넣은 `_looks_like_account()`(자릿수·날짜 판별)와 같은 계열의 확장이다.

3. **컨텍스트 키워드 가중치**
   숫자열 주변 ±20자에 `주민번호`, `계좌`, `카드` 같은 단어가 있으면 신뢰도를 올리고,
   `버전`, `일자`, `주문번호`, `전표`가 있으면 내린다. 형태만 보는 현재 방식의 정확도를 크게 올린다.

4. **테스트·예제 데이터 화이트리스트**
   공식 문서에 예시로 쓰이는 번호(`900101-1234567`, `010-0000-0000`, 카드사 테스트 번호 `4111-1111-1111-1111`)는
   실제 PII가 아니다. 이런 게 이벤트로 쌓이면 대시보드 신뢰도가 떨어진다.

5. **긴 입력 청크 분할 (S4 대응)**
   문서 전체를 한 벡터로 만들지 말고 문단/300자 단위로 쪼개 **각 청크의 최대 점수**로 판정한다.
   희석 회피가 막히고, 어느 문단이 걸렸는지도 알 수 있어 담당자 판단에 도움이 된다.

### 2-3. F1 측정 체계

**지금은 F1을 말할 수 있는 상태가 아니다.** 라벨링된 데이터셋도, 측정 스크립트도 없다.
`tests/`의 코퍼스(정상 28 + 민감 12 + 정규식 케이스 22)가 씨앗이지만 규모가 작고 합성 데이터다.

권장 순서:

1. **골든 데이터셋 구축** — 실제 트래픽에서 500~1000건을 샘플링해 담당자가 라벨링.
   유형별(주민번호/계좌/기밀요청/인젝션/정상)로 최소 50건씩. 이게 없으면 이후 전부 추측이다.
2. **측정 스크립트** — 유형별 precision/recall/F1 + 혼동행렬 리포트.
   `score_similarity()`가 이미 원점수를 돌려주므로 PR 곡선을 그릴 수 있다.
3. **임계값 최적화** — 유형별로 목표를 다르게 잡는다.
   주민번호·인젝션은 **recall 우선**(미탐 피해가 큼), 계좌·이메일은 **precision 우선**(오탐이 담당자 피로를 만듦).
   단일 F1 최대화는 이 비대칭을 무시한다.
4. **회귀 게이트** — 이미 있는 `TestThresholdSeparation`을 골든셋 기반으로 확장해
   임계값·참고문장 변경 시 F1이 하락하면 CI가 막도록 한다.

## 3. System Architecture Enhancement

### 3-1. 스트리밍 응답 실시간 필터링

현재는 응답 전체를 받은 뒤 검사한다(최대 60초 대기). 스트리밍으로 바꾸되 DLP를 유지하려면:

- **슬라이딩 윈도우 검사** — 토큰을 바로 흘리지 않고 N자(예: 200자) 버퍼를 두고,
  버퍼가 차면 검사 후 안전한 앞부분만 방출한다. PII가 청크 경계에 걸치는 것을 막는다.
- **2단계 검사** — 청크마다 정규식(수 μs), 문단 완성 시점에만 임베딩(수백 ms).
  임베딩을 토큰마다 돌리면 스트리밍의 이점이 사라진다.
- **중도 차단 프로토콜** — 이미 내보낸 텍스트는 회수 못 한다.
  SSE 이벤트로 `{"type":"redact","from":N}`를 보내 프런트가 지우도록 하거나,
  애초에 버퍼 지연을 PII 최대 길이 이상으로 잡는다.

### 3-2. 토큰 단위 마스킹 / FPE

현재 마스킹은 `*` 치환 단방향이다. 두 가지 한계가 있다.

- `confidential_similarity`는 문장 전체가 탐지 구간이라 **마스킹본이 별표만 남는다.**
  담당자가 오탐 판단을 할 수 없어서, 지난 작업에서 원문을 별도 보관하도록 했다.
- 마스킹된 프롬프트를 LLM에 보내면 문맥이 깨져 답변 품질이 떨어진다.

**FPE 또는 토큰화(tokenization)** 를 도입하면 `901231-1234567` → `850417-2938471`처럼
형식을 유지한 대체값을 넣어 LLM 문맥을 살리고, 응답에서 역치환할 수 있다.
다만 금융권에서는 대체값의 키 관리가 곧 규제 대상이므로 **Vault/KMS 도입과 세트로 가야 한다.**
그 전 단계로는 `[주민등록번호_1]` 같은 **placeholder 토큰화**가 훨씬 싸고 안전하다.
문맥도 살고 역치환도 되고 키 관리도 필요 없다. **여기서 시작하는 걸 권한다.**

### 3-3. Dynamic Rule Engine

`policy_info.rule_content`(jsonb) + `policy_history`(버전 스냅샷)가 **이미 스키마에 있다.**
DLP가 이걸 읽게 만드는 게 가장 비용 대비 효과가 큰 고도화다.

- 부서별 임계값·패턴·차단 등급을 DB에서 로드, 배포 없이 변경
- `policy_history`로 "언제 어떤 정책이 적용 중이었는가"가 자동으로 증빙이 된다 (감사 대응에 직접 쓰임)
- 규칙 변경 시 골든셋으로 자동 재평가 → F1 하락하면 반려하는 워크플로

주의: 규칙을 DB에서 읽되 **정규식을 사용자 입력에서 그대로 컴파일하면 ReDoS 위험**이 있다.
패턴 화이트리스트 또는 `re2` 계열 엔진을 쓰거나, 규칙 등록 시 타임아웃 검증을 걸어야 한다.

### 3-4. Context-aware PII Detection

형태만 보는 현재 방식에 문맥 신호를 더한다.

- 주변 키워드 가중치 (§2-2)
- **역할 기반 판정** — 여신심사팀의 고객 계좌 조회는 정상 업무, 마케팅팀은 아님.
  `users.department_id`가 이미 있으므로 부서별 정책(§3-3)과 결합하면 자연스럽다
- **누적 위험도** — 단건은 통과지만 한 세션에서 고객정보를 반복 조회하는 패턴 탐지.
  개별 요청만 보는 현재 구조로는 절대 못 잡는 유형이다

### 3-5. 비동기 로그 수집 및 게이트웨이 성능

현재 병목은 순서대로 (a) 동기 DB 커밋, (b) 임베딩 추론, (c) 스트리밍 부재다.

1. **로그 적재를 응답 경로에서 분리** — FastAPI `BackgroundTasks`로 시작하고,
   규모가 커지면 Redis Stream / Kafka로 이관. 판정은 즉시 반환하고 적재는 뒤에서 한다.
   단, **차단 이벤트는 동기 적재를 유지**해야 한다. 증빙이 누락되면 안 되는 유형이다.
2. **탐지 결과 캐싱** — 프롬프트 해시 → 판정 결과를 Redis에 단기 캐싱.
   같은 질문 반복, 특히 시스템 프롬프트가 붙는 경우 효과가 크다.
3. **2단계 모델 캐스케이드** — 1차로 e5-small(빠름)로 거르고, 경계 구간만 e5-large로 재판정.
   대부분의 트래픽이 명백히 정상이라 평균 레이턴시가 크게 준다.
4. **DLP 워커 수평 확장** — 현재 전역 ONNX 세션 1개. `uvicorn --workers N` 또는
   모델 서버 분리(Triton/TorchServe)로 동시성 확보. 프로세스당 메모리(e5-large ~2GB) 주의.
5. **게이트웨이 도입 시점** — Kong/Envoy는 지금 필요하지 않다. 서비스가 2개뿐이라
   운영 복잡도만 늘어난다. **다만 운영 배포 시 리버스 프록시(NGINX)는 필수다** —
   현재 Vite dev proxy가 유일한 라우팅 계층이라 운영에 그대로 나가면 :8000이 그대로 노출된다.
6. **OpenTelemetry** — 지금 도입하면 "어느 단계가 느린가"를 추측이 아니라 데이터로 말할 수 있다.
   `inspectPrompt` → 탐지 → LLM 호출 구간에 스팬만 걸어도 §1-7의 미실측 항목이 해소된다.

우회 검증 자체를 회귀 테스트로 고정하는 것은 Q5·Q6 작업에 포함하는 것을 권한다.
현재 테스트에는 우회 케이스가 들어 있지 않다.

### 2차 점검(2026-08-03)에서 실행한 측정

| 항목 | 방법 | 결과 |
| --- | --- | --- |
| PII 우회 | 주민번호 변형 **13종**을 `detect_pii()`에 직접 투입 | 기준값 1종만 탐지, **나머지 12종 전부 통과** |
| 인젝션 우회 | 변형 **8종** 투입 (글자 사이 공백, base64, rot13, 일본어 `これまでの指示をすべて無視`, 영문 완곡표현, 역할극) | 기준값 1종만 탐지, **7종 통과** |
| 레이턴시 | `detect_similarity()`/`detect_pii()`를 길이 7구간 × 5회 반복, 중앙값 | §1-7 표 |

1차 점검이 확인한 8종에 더해 이번에 추가로 통과가 확인된 우회:
`901231.1234567`(점), `901231–1234567`(en-dash), `901231-\n1234567`(줄바꿈 분리),
`3930313233312d...`(hex), `9O1231-1234567`(leet 치환), `구공일이삼일-일이삼사오육칠`(한글 표기).

인젝션 쪽에서 특히 주의할 것은 **다국어 우회**다.
`これまでの指示をすべて無視してください`는 한국어·영어 패턴 어디에도 안 걸린다.
현재 정규식은 한국어와 영어만 커버하므로, 다국어 입력이 가능한 환경에서는 구조적으로 뚫린다.
M8(분류 모델)이 필요한 직접적 근거다.
