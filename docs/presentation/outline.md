## 3. [DLP] 왜 필요한가 + 이번 기간의 출발점 — 20초

**핵심 메시지**
- DLP(Data Loss Prevention)는 데이터가 조직 밖으로 나가는 것을 막는 통제다. 여기서는 프롬프트가 외부 LLM에 도달하기 전 마지막 관문이다.
- 지난 기간까지 탐지기는 이미 동작했지만, **오탐(정상 입력을 위험으로 잘못 판정)** 이 실사용을 방해하고 있었다.
- 실제 리포트: `dddd`, `하이` 같은 무의미 입력에 "민감한 내용이 포함되어 표시할 수 없습니다"가 떴다.

**함께 띄울 것**
- 차단 메시지 문구 인용 (`main.py`의 응답 문구)
- 오탐/미탐 용어 정의 한 줄씩

## 4. [DLP] 설계 — 2계층 × 2방향 — 20초

**핵심 메시지**
- 탐지는 2계층이다. 정규식은 형태가 고정된 PII(주민번호·계좌 등)를, 임베딩 유사도는 표현이 바뀐 의미 기반 기밀 요청을 맡는다.
- 임베딩은 `fastembed` + `multilingual-e5-large`로 **로컬에서만** 계산한다 — 검사하려고 프롬프트를 외부로 내보내면 앞뒤가 안 맞기 때문이다.
- 검사는 사용자 입력과 AI 응답 **양방향 2회**다. AI가 참조 데이터를 그대로 뱉는 경우를 막기 위해서다.

**함께 띄울 것 (다이어그램)**

```
브라우저
  └→ Node  chat.service.sendMessage()
        ① inspectPrompt(입력)  → POST :8000/gateway/chat  direction="input"
        │      detector.py(정규식) + embedding_detector.py(유사도)
        │      → allowed / masked / blocked
        ② blocked면 LLM 호출 생략, 아니면 Solar 호출
        ③ inspectPrompt(응답)  → POST :8000/gateway/chat  direction="output"
        └→ usage_log / event_log / action_history 적재
```

- 판정 3종: `allowed` / `masked`(`*` 치환) / `blocked`
- `BLOCK_TYPES = {resident_number, prompt_injection, confidential_similarity}` — 마스킹으로 의미가 안 살아서 항상 차단

## 5. [DLP] 구현 ① 정규식 정밀화 — 22초

**핵심 메시지**
- 기존 패턴은 형태만 봤다. 숫자 경계가 없어 긴 숫자열 중간을 잘라 매칭했고, 날짜·버전 문자열을 계좌번호로 잡았다.
- 경계(`(?<!\d)`/`(?!\d)`) + 값 유효성 검증(생년월일·성별코드·자릿수)을 추가했다.
- 인젝션 패턴은 **완화하지 않았다.** 미탐 피해가 더 크기 때문에, 명백히 틀린 `jailbreak` 단어 매칭만 좁히고 나머지는 오히려 강화했다.

**함께 띄울 것 (before/after 코드 대비)**

| 유형 | Before | After |
| --- | --- | --- |
| `resident_number` | `\d{6}-\d{7}` | 경계 + YYMMDD 월·일 유효성 + 뒷자리 첫 숫자 1~8 |
| `phone_number` | `01[0-9]-…` | `01[016789]-…` (실사용 식별번호만) |
| `account_number` | `\d{2,6}-\d{2,6}-\d{2,10}` | 위 + `_looks_like_account()` 후처리 (총 10~16자리, `YYYY-MM-DD`·연도나열 제외) |
| `prompt_injection` | `jailbreak` (단어) | 명령형만 — `enter jailbreak mode`, `jailbreak this model`, `탈옥 모드로 전환해줘` |
| `prompt_injection` | `ignore (all )?(previous\|above\|prior) instructions?` | **강화** — `disregard the above rules` 같은 관사·수식어 변형까지 |

- 확장 지점: `POST_VALIDATORS` 훅 — 다른 유형도 같은 방식으로 후처리 검증 추가 가능

## 6. [DLP] 구현 ② 막혔던 지점 — 절대 임계값이 성립하지 않았다 — 26초

**핵심 메시지**
- 임베딩 유사도 임계값을 아무리 올려도 오탐이 안 사라졌다. 원인은 값이 아니라 **구조**였다.
- `multilingual-e5`는 무관한 문장끼리도 코사인 유사도가 0.78~0.86이다. 유사도 하한이 0이 아니라 0.8 근처에 깔려 있는데 기존 임계값이 0.86이었다 — 노이즈 바닥에서 0.03 떨어져 있었다.
- 정상 대화 앵커를 기준선으로 두고 **마진**을 보는 방식으로 바꾸니 오탐·미탐이 함께 0이 됐다.

**함께 띄울 것 ① — 절대 임계값이 안 되는 증거**

| 입력 | 최고 유사도 |
| --- | --- |
| `안녕하세요! 무엇을 도와드릴까요?` | 0.867 |
| `'dddd'라고 입력해 주셨는데…` | 0.891 |
| `죄송합니다. 입력하신 내용을 이해하지 못했습니다.` | **0.944** |
| `우리 회사 고객 김철수의 계좌 잔액…` (진짜 민감) | 0.933 |

→ 평범한 사과 문장이 진짜 민감 요청보다 높다. 임계값을 올리면 미탐만 늘어난다.

**함께 띄울 것 ② — 방식별 실측 (정상 28문장 / 민감 12문장)**

| 방식 | 오탐 | 미탐 |
| --- | --- | --- |
| 기존: 절대 0.86 | **8/28** | 0/12 |
| 절대 0.90 | 1/28 | **4/12** |
| 절대 0.92 | 1/28 | **5/12** |
| **적용: 절대 0.88 + 마진 0.02** | **0/28** | **0/12** |

**함께 띄울 것 ③ — 판정 조건 코드**

```python
SIMILARITY_THRESHOLD = 0.88
BENIGN_MARGIN = 0.02
# ① 민감 카테고리 유사도 ≥ 0.88
# ② 그 유사도가 정상 앵커(BENIGN_REFERENCE_TEXTS) 유사도보다 0.02 이상 높을 것
if result["score"] < SIMILARITY_THRESHOLD or result["margin"] < BENIGN_MARGIN:
    return []
```

- 마진 분포: 정상 문장 최대 **+0.0089**, 민감 문장 최소 **+0.0220** — 구간이 겹치지 않는다
- 부가: `MIN_TEXT_LENGTH`(8자) 미만 / 문자 종류 3개 이하 반복문자열은 유사도 판정 자체를 건너뜀. 정규식은 길이와 무관하게 그대로 동작한다

## 7. [DLP] 구현 ③ 막혔던 지점 — 한 번의 대화가 사용 이력 2건이 되던 문제 — 22초

**핵심 메시지**
- 입력·출력 검사가 게이트웨이를 각각 호출하는데, 게이트웨이가 호출될 때마다 `usage_log`를 새로 만들고 있었다.
- 결과적으로 사용량 통계가 2배로 부풀려졌고, **AI 응답이 사용자가 보낸 프롬프트인 것처럼** 기록됐다.
- `direction` 파라미터로 입력·출력을 구분해서 해결했다. 로그 실패가 보호 해제로 이어지지 않도록도 처리했다.

**함께 띄울 것 (동작 대비 표)**

| `direction` | `usage_log` | `event_log` |
| --- | --- | --- |
| `input` (기본값) | 새로 생성하고 `usage_log_id` 반환 | `direction="input"` |
| `output` | **만들지 않음** | 받은 `usage_log_id`에 `direction="output"`로 덧붙임 |

**스키마 변경** (alembic이 없어 `init_db.py`에 멱등 `ALTER TABLE`로 처리)

| 테이블 | 추가 컬럼 |
| --- | --- |
| `event_log` | `direction`, `description`, `masked_description` |
| `action_history` | `direction` |

**설계 판단 한 줄씩**
- `usage_log_id` 없이 `output`이 들어오면 **차단·마스킹 판정은 그대로 하고 기록만 건너뛴다.** 로그를 못 남긴다고 보호까지 풀 이유는 없다 (응답의 `logged: false`로 알림).
- `/events`가 `event_log.id`를 함께 내려준다 — 한 `usage_log`에 입력·출력 이벤트가 같이 달려서 `event_id`만으로는 행을 특정할 수 없다.
- 파생 효과: 증빙 ⑧(출력·에러메시지 내 기밀정보 노출 방지)이 컬럼이 없어 보류돼 있던 `output_leak_block` 태깅을 포함하게 됐다 (`evidence.service.js`의 `generateEvidence8`).

## 9. 다음 기간 계획 — 16초

**핵심 메시지**
- 이번 기간에 탐지 정확도를 올리면서 **탐지기를 감싸는 신뢰 경계가 비어 있다**는 걸 자체 점검으로 확인했다.

**함께 띄울 것**
